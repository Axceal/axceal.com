# Waitlist Gating Plan

Canonical execution doc. Resume work from first unchecked "Done criteria" box. Any deviation updates this file in the same commit.

## Goal

Pre-launch gate: site visitors create an Axceal account to join purchase queue. Block all checkout flows. Post-launch flip via env flag reopens normal purchase. Existing accounts are queue members. Position assignment robust against user deletions.

## Invariants

- **Position is stable.** Assigned once at join, never recomputed. Deletes leave gaps. Sequence never reissues a value.
- **Position counter via Postgres sequence** `waitlist_position_seq START 1001`. Independent of row count.
- **Dummies are out of scope.** Existing dummy/test accounts (positions reserved #1–#1000) are deleted manually by Varun before launch. Plan does not backfill them.
- **Real existing users at flag-flip time:** auto-joined silently on next authenticated request (idempotent insert in session callback or middleware tap). New value from sequence.
- **No total count displayed.** Users only see their own number.
- **No address collection in waitlist mode.** `/account/details` and address flows untouched but unreachable via CTA.
- **Server-side join.** `POST /api/waitlist/join` called from `account-create` handler after password set. No client fetch after redirect → CSRF token churn avoided.
- **Money-format unchanged.** Live mode shows `AERO.priceInPaise` formatted INR in CTA sub-label slot.

## Sales mode flag

Three values, single env var, public prefix (client + server both branch on it):

```
NEXT_PUBLIC_SALES_MODE = "waitlist" | "live" | "dev-live"
```

| value      | meaning                                                                  |
|------------|--------------------------------------------------------------------------|
| `waitlist` | default. Production pre-launch. Checkout disabled. Popups active.        |
| `live`     | production post-launch. Normal purchase flow. Waitlist endpoints → 410.  |
| `dev-live` | dev-only override. Behaves like `live` but env.ts rejects in prod build. |

- `lib/featureFlags.ts` exports `SALES_MODE`, `isWaitlist()`, `isLive()` (true for both `live` and `dev-live`).
- `lib/env.ts` Zod enum, default `waitlist`. Production build hard-rejects `dev-live` (mirrors existing `NEXT_PUBLIC_DEV_SKIP_AUTH_GATES` guard).

## Data model

Migration `drizzle/0004_waitlist.sql`:

```sql
CREATE SEQUENCE waitlist_position_seq START 1001;

CREATE TABLE waitlist (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  position integer NOT NULL DEFAULT nextval('waitlist_position_seq'),
  joined_at timestamptz NOT NULL DEFAULT now(),
  invited_at timestamptz,
  converted_order_id uuid REFERENCES orders(id)
);
CREATE INDEX waitlist_position_idx ON waitlist(position);
```

Drizzle schema mirror in `lib/db/schema.ts`. `position` not auto-generated by Drizzle insert — DB default fires.

Cascade delete = waitlist row dies with user. Sequence keeps climbing → retired numbers never reissued.

## Contracts (`lib/contracts/waitlist.ts`)

- `WaitlistStatusResponse = { inQueue: boolean; position: number | null; joinedAt: string | null }`
- No request body for join — derived from session.

## Service (`lib/services/waitlist.ts`)

- `join(userId): Promise<{ position: number }>` — `INSERT ... ON CONFLICT (user_id) DO NOTHING RETURNING position`. If no row returned, `SELECT position WHERE user_id = $1`. Idempotent.
- `getStatus(userId): Promise<WaitlistStatusResponse>`
- Internal guard: throw if `isLive()` — defense in depth against accidental callers post-launch.

## API routes

| route                          | method | mode behavior                                                       |
|--------------------------------|--------|---------------------------------------------------------------------|
| `/api/waitlist/join`           | POST   | waitlist: auth required, idempotent join. live: 410 Gone.           |
| `/api/waitlist/status`         | GET    | waitlist: auth required, returns status. live: 410 Gone.            |

All through `withHandler` envelope. CSRF middleware applies (mutating + non-exempt).

## Middleware changes (`middleware.ts`)

Add waitlist gate that runs **before** auth gate:

```ts
const WAITLIST_BLOCKED_PAGE = [/^\/order(\/|$)/];
const WAITLIST_BLOCKED_API = [
  /^\/api\/orders(\/|$)/,
  /^\/api\/payments\/(initiate|verify)(\/|$)/,
  /^\/api\/addresses(\/|$)/,
];
```

If `isWaitlist()`:
- page in blocked list → redirect `/`
- API in blocked list → 403 `{ code: "SALES_DISABLED" }`

Auto-join hook: in `auth/config.ts` session callback, if `isWaitlist()` and user has no waitlist row, insert one. Single best-effort upsert per session creation (not per request).

## Frontend

### Flag-driven CTA on home

Single "Get One" button in `app/HomeClient.tsx` and `app/components/home/MobileHome.tsx`. Sub-label slot driven by `SALES_MODE`:

| state                                | left pill   | right sub-label                              | on click                          |
|--------------------------------------|-------------|----------------------------------------------|-----------------------------------|
| waitlist, unauth                     | "Get One"   | "Queue Me Up"                                | open popup-1                      |
| waitlist, authed (in queue)          | "Get One"   | `#{position.toLocaleString()}` e.g. `#1,247` | open popup-2                      |
| live / dev-live, any                 | "Get One"   | `formatINR(AERO.priceInPaise)` e.g. `₹9,999` | link `/order/units` (existing)    |

Position for sub-label loaded via `useSession` augmentation or single `/api/waitlist/status` fetch on mount when authed.

### Popup component

`app/components/waitlist/WaitlistDialog.tsx` — single component, two variants.

**Variant `join` (popup-1):**
- Title: "Join the queue to be among the first to get Aero by creating an Axceal account"
- Sub: "Queue up at #{nextPosition}"  (next sequence value, fetched live)
- Buttons: `Cancel` (red text, closes) · `Create Account` (blue, navigates `/create-account?intent=waitlist`)

**Variant `status` (popup-2):**
- Title: "Your Axceal account is already in the queue"
- Sub: "Keep an eye on your inbox for an email"
- Footer: "Queue up at #{position}" + `Okay` button (closes)

Mounted once in `app/layout.tsx`. Opened via React context dispatched from CTA. No global route changes.

`nextPosition` for popup-1 fetched from new `GET /api/waitlist/next` (public, no auth, returns `nextval` peek via `last_value + 1` from `waitlist_position_seq` — read-only, no consumption). Cache 30s on the edge.

### Create-account flow change

`?intent=waitlist` query param tracked through OTP + password steps. On final account-create handler success:
1. Server-side: insert waitlist row → `position`.
2. Return `{ user, waitlist: { position } }` in response.
3. Client redirects `/` with `?joined=1`.
4. Home reads `?joined=1`, opens popup-2 once with the position.

### AccountShell

Waitlist mode: hide Orders card. Show small "Waitlist · #1,247" chip linking nowhere (informational). No new route.
